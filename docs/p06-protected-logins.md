# Protected reusable logins

Open **Protected login entry** in the paired workspace or from a conversational Vault handoff. Choose a public label, one exact HTTPS origin and bot scope. macOS collects the private username, password and optional TOTP seed in native `NSSecureTextField` controls. Other platforms refuse private entry. The bot's value-free handoff also returns accessible item identifiers, revisions and origins; it never returns stored values.

Save and rotation use a bounded binary owner frame outside `OwnerOperation` and the native mutation journal. The native service persists a request identifier and value-free receipt before sending, clears private controls and never automatically resends values. **Reconcile receipt** establishes either the committed item or final closure before explicit re-entry. Manager closure and writes share the state actor, so a late write cannot commit after closure. Unlock uses the same ephemeral boundary.

List login metadata to rotate, remove or replace an item's metadata with the form values. Metadata changes clear remembered rules and revoke pending uses. **Forget rules** clears rules without changing metadata. Removal is a tombstone; retired encrypted epochs remain available for screening. Lock revokes pending uses and requests cancellation of releases still awaiting settlement.

## Supported filling

A bot selects `ComputerOperation::ProtectedLogin` as its sole Computer operation, with no output declarations. Normal task approval admits that supervised process. The browser then parks on the actual form while the owner reviews a separate credential request in the paired workspace. Its review shows the item revision, purpose, origin, exact POST destination, field names and types, document identities, task, bot, session and execution fences. **Allow once** permits only that fill and native form submission.

Version 1 supports a top-level native HTML form or one same-origin child frame. It requires HTTPS, exact public paths without query strings, a POST with URL-encoded form data, unique visible enabled inputs and a submit button without overrides. The form must contain only the approved username/password inputs or one TOTP input plus its submit button. Hidden CSRF fields, custom JavaScript login submission, cross-origin or deeper frames, redirects and ambiguous selectors refuse. A form marked `data-botstral-login="v1"` is classified as supported for remembering; the owner still approves the first exact rule. Other supported native forms require a fresh review every time. This marker is a site contract, not a claim that the site is trustworthy.

The runtime holds actual document and element references in a Chromium isolated world. It validates the same objects before release and synchronously before assignment, checks that the browser preserved the exact values, dispatches input events, then revalidates around native form submission. A paused navigation must match the exact POST, frame and field payload, and the original synchronous DOM call must confirm that form-data handlers left the contract unchanged before the request can proceed. Top or frame reloads, replaced elements, changed names, types, visibility, ownership, actions, methods and submitter overrides refuse. Redirect responses are stopped before following them. Playwright routing alone [only handles the first request of a redirect chain](https://playwright.dev/docs/api/class-page#page-route); the adapter also uses Chromium response interception.

Website scripts can read values filled into their document. Botstral cannot revoke a value already delivered to the site. An `applied` receipt means the approved form submission was invoked; it does not assert successful website authentication. The controlled acceptance server separately verifies sign-in.

## Policy and release

Current item state, bot scope, Computer permission, parent task, worker connection generation, journal incarnation, input ownership, revisions and deadlines must all authorize release. A matching deny wins over allow-once and remembered allows. TOTP, every-fill policy and uncertain classification always require fresh approval. Only the remaining password branch can use an exact remembered rule. Rules bind the item and bot, top/frame origins, supported plan and field role/name/type shape. Remembering advances the item revision and requires re-preparation; older reviews cannot release. Preparation retries return the same review and deadline, including after settlement. Each admitted parent permits one initial review and one exact remembered-password successor. Another fill requires a new admitted task. A changed destination refuses. The successor cannot extend the initial deadline.

**Deny and remember** persists a denial of that exact contract. Clear its rules before trying again. Remembered rules permit no unrelated click, purchase, message or other Computer operation. New tasks and document instances obtain new use identifiers. Each release is consumed before response transmission. Dropped responses cannot retrieve the payload again. Expired or revoked releases without settlement become explicitly uncertain in owner review history.

The manager alone decrypts TOTP seeds and generates codes. Supported seeds are canonical uppercase unpadded Base32, 32–128 characters. Codes use HMAC-SHA-1, six digits and a 30-second period, with at least five seconds remaining at release. Every TOTP fill needs fresh approval. All SHA-1 vectors from [RFC 6238 Appendix B](https://www.rfc-editor.org/rfc/rfc6238#appendix-B) verify the algorithm. Issued codes are encrypted and retained for disclosure screening.

Install and reseal the updated runtime with `agent/runtime/setup.sh` before using protected fills on Linux; an older Computer runtime cannot execute the new operation.

The worker exposes a private per-execution Unix socket to the admitted process scope. It derives authority from its journal, checks the peer UID and Linux cgroup, and uses a separate bounded mutual-TLS request to the manager. Values never enter ordinary worker commands, manifests, arguments or environment. One cancellable private request runs independently of the worker connection loop. It cannot delay cancellation processing.

## Capture and retention

Before a possible release, the worker durably records the release identifier against the actual shared profile. The marker survives task completion, logout, item removal and restart. A changed worker journal persists incomplete provenance before launching a runtime. Missing or corrupt records refuse capture; they cannot convert an existing browser profile into a clear profile.

The profile marker also records possible releases. It must match the worker's release history before capture can be clear. Restoring older worker metadata against a newer profile, or interrupting publication between those records, refuses capture. Legacy markers cannot establish complete coverage. Private release starts only after both records are durable.

Protected text crosses the private channel for manager screening before the runtime writes an output. The manager verifies profile ownership against immutable task assignment and requires the exact complete set of recorded emitted releases. Unknown profiles, duplicate identifiers, missing history, locked decryption and inconsistent provenance withhold the observation. A known prepared profile with no emitted releases can screen without consulting secret inventory. Password releases screen only the delivered username and password; TOTP releases screen only the exact issued code. Rotation, removal and expired authority do not erase this retained protection. The manager also decrypts each recorded login epoch to establish its integrity. A snapshot restored before code issuance cannot establish coverage even if it contains the earlier authorized review.

Worker profile screening never compares text with seeds or unrelated login, provider, connector or issued-code values. Ordinary public-channel screening retains its broader inventory. Both paths check literal, JSON-escaped, percent-encoded and common Base64 forms. These checks do not cover arbitrary transformations or covert channels.

Screenshots and recordings of protected state, downloads, binary exports and ordinary file reads/exports remain refused. Profile, execution, socket and runtime paths are also blocked through resolved aliases. There is no pixel-redaction claim. Safe screened text and fixed value-free outcomes remain available.

Limits refuse new operations instead of deleting screening history: 64 items, 512 login epochs, 4,096 write receipts, 4,096 use records, 256 rules, 512 issued codes and 64 possible releases per actual profile. The first valid preparation attempt is durably claimed before comparing its public destination with global secret inventory. A rejected comparison or crash before review creation closes that parent; recovery requires a new admitted task. Cached retries do not consume capacity or repeat that comparison. At most one destination comparison remains per owner-admitted parent. A profile that reaches its limit needs a verified empty replacement after its old scopes stop; this implementation has no control that preserves old cookies while clearing protection.

## Recovery and limits

Age ciphertext authenticates the installation, item, encrypted epoch and kind; issued-code binding also includes its release identifier. Backups retain encrypted identity, login/code histories, policies, rules, receipts and preparation claims. Manager schema 16 migrates existing stores without deleting retained history. Startup and restoration remain locked. Explicit unlock needs the owner-provisioned passphrase; a backup cannot recover an unavailable passphrase. Older manager backups restore older policy and revocation state, so the owner must reconcile later changes. Worker release provenance remains independently conservative.

Removing or rotating a login does not log out website sessions or revoke cookies, copied credentials or remote grants. Historical encrypted values remain in the manager and backups. These controls do not establish secrecy from arbitrary code with full shared guest privileges. Rust-owned private buffers are cleared when dropped; browser, JavaScript, transport-library and operating-system memory cannot be guaranteed to zeroize.

Run `python3 scripts/verify-p06.py --full` after installing workspace dependencies, `npm ci --prefix agent/runtime --ignore-scripts` and `node agent/runtime/node_modules/playwright/cli.js install chromium`. The macOS browser fixture uses system Chrome unless `BOTSTRAL_CHROME` is supplied. It also uses Playwright Chromium for full-runtime capture and approval-component checks. Each invocation retains command exits and evidence under `docs/evidence/p06/`.

The packaged macOS-to-Linux workflow and actual Linux cgroup/private-TLS release have passed on their recorded source revisions. [The acceptance record](evidence/p06/final-acceptance.md) separates those runs from bridge-backed component checks and later source changes. Exact final-source broad and Linux verification passed, and independent review accepts the supported v1 code. PLAN records the verified rows; host reboot verification and manual takeover remain open.

Approvals retain their originating paired device and grant epoch. Revoking that device invalidates its one-shot and remembered approvals and requests durable cancellation of its released work. Disconnecting a device does not revoke its durable approvals. Old remembered rules without recorded approval provenance require fresh approval.

Native write receipts retain the authenticated manager identity. Switching managers cannot close an unresolved original receipt. Reconnect to its original manager to reconcile it. Receipts without verifiable manager identity refuse reconciliation.

Private values that overlap mandatory public application text are refused before storage, including synthetic `admin` and `owner` usernames. The final rejection receipt contains no private value. A rejected rotation preserves the existing item. Choose a different private value or sign-in account. The intake check uses the generated shared protocol and typed provider-message schemas, the actual provider envelope and prompt builders, current typed model configurations, recovered memory context, and stored public item, receipt and review records, including historical metadata. It covers fixed request fields and message discriminators as well as provider instructions. It does not promise that arbitrary future site content or user text cannot independently match a retained value; that observation still refuses.

Unpublished pre-fix stores that accepted a colliding value need an explicit restore of a manager backup taken before that entry. Stop the manager and follow the existing offline recovery procedure. Preserve the affected store separately and do not delete retired encrypted epochs to bypass screening. The regression constructs a legacy affected epoch, verifies that removal cannot unblock disclosure screening, restores a pre-entry SQLite snapshot, and verifies benign conversation again. Existing protected browser profiles whose releases are missing from the restored manager remain withheld. Reset or provision a separate Computer worker through an explicit recovery decision before using its browser; restoring manager history does not establish coverage of a newer browser profile. Without a pre-entry backup, this version provides no automatic repair.

The browser process closes between Computer calls. Persistent cookies can survive; session-only cookies are not promised to survive a new process. The controlled multi-step Linux fixture therefore issues an explicit persistent session cookie. An `applied` use means the approved form was submitted; the receiving site's authentication result must be checked separately.

Generated TOTP codes pass the same public-context check before retention or private release. A code that coincides with current configuration or public context refuses without entering retained secret inventory. A failed fill can leave its possible-release browser profile conservatively withheld. Use a verified empty replacement when complete coverage cannot be established; the app does not automatically reset profiles or preserve their old cookies while clearing protection.

Existing enabled connector definitions across all live bots are included in prospective private-value checks, together with the exact names and schemas sent to providers. A collision receives a final refusal before a new epoch or current code enters retained inventory. This protects existing connector-enabled conversations as well as plain chat. Later arbitrary catalog updates can still introduce new matching content and refuse publication.
